Monitoring the AI

How to see what the AI plane is doing at runtime — whether it’s live or mocked, whether calls are succeeding, and when the model is degrading.

● structured logs health & config endpoints graceful, logged degradation
01

What you can observe today

Offline evals prove quality before a release. This page is about the signals while it runs — the runtime picture of the AI plane once real notes are flowing through it.

WHY SEPARATE Evals and monitoring answer two different questions, and neither replaces the other. Evals run on a fixed golden set in a controlled harness and ask “is this build good enough to ship?” — a gate you pass once, before release. Monitoring runs continuously on live traffic and asks “what’s actually happening right now?” The real inputs, model, quota, and network are all things a pre-release check can never see. A build that scored perfectly in evals can still fall back to the mock in production because NIM is down. Monitoring exists to close that gap between “proven good” and “behaving well.”

Where it stands today. Monitoring today is structured logs, the health and config endpoints, eval scores, and graceful, logged degradation. There are no metrics, distributed tracing, or alerting yet — those are on the roadmap. But the design already emits everything a collector needs.

1 · Structured logs

The primary signal. Every hop writes machine-readable log lines that any collector can ingest — no dashboards required to start reading them.

WHY JSON One JSON object per line is the whole trick. An unstructured print("extraction failed for note 42") is a string a human can read and nothing more — counting failures means writing brittle regexes, and every developer phrases the message slightly differently. A structured line like {"level":"warn","msg":"note extraction failed","noteId":42,"time":"…"} is a record. You can grep it, jq it, filter on level, and group by noteId, and any log collector — Loki, Application Insights, a plain tail — can ingest it without a custom parser. Because the format is decided in one place, the sink is swappable: point logger.ts at a different backend and every call site keeps working untouched. That’s the payoff of structuring at the source rather than at the reader.

App — Next.js

src/lib/logger.ts emits one JSON object per line (level, message, time, plus fields), greppable and ingestible by any collector. LOG_LEVEL (debug|info|warn|error) sets the threshold — info in production, debug in dev. Notable AI events: ward extraction complete with { processed, failed, barriers, ungrounded }; ward extraction failed and per-note note extraction failed with the error; and AI config fetch failed when the Settings card can’t reach the AI plane.

AI plane — FastAPI

Python logging under wardbeat.ai. Notable events: AI plane up — mock=<bool> model=<id> rpm=<n> at startup, NIM extraction failed (…); using mock fallback when a live call falls back, reranker unavailable on this tier; using cosine order, and other per-capability … failed (…); using mock warnings. Tail it in dev with docker compose logs -f ai.

2 · Health & configuration endpoints

Two internal endpoints answer the two questions that matter first: is the AI plane up, and is it live or mocked?

Endpoint Auth Tells you
GET /healthz none (liveness) { status, mock, model } — whether it’s up, and live or mocked.
GET /config service token Full non-sensitive config: mode, model ids, endpoint host, rate limit, timeout, embedding dimension, and whether the key and token are configured — the values themselves are never exposed.

WHY TWO The split is deliberate. /healthz is a liveness probe — what an orchestrator, load balancer, or uptime check hits every few seconds to decide whether the container is alive. It stays unauthenticated because a probe can’t carry a credential, and it stays minimal because it must be cheap to answer under constant polling and must never leak anything sensitive. { status, mock, model } is safe to expose to anyone. /config is the opposite: the full internal picture — endpoint host, rate limits, timeouts, which credentials are present — useful to an operator debugging, but exactly the kind of surface you don’t want open to the world. So it sits behind a service token. Same idea, two audiences: a robot health check that must be open and tiny, and a human config view that must be gated.

3 · The AI-configuration Settings card

Settings → System → AI configuration (admin-only) renders /config as an operability surface: Reachable / Unreachable, Live / Mock, the three model ids, the endpoint host, the operational limits, and credential presence. It’s the fastest way to confirm from the product itself that the AI plane is wired and reachable — no shell access needed (src/components/settings/ai-config-card.tsx).

4 · Graceful, logged degradation

Every model call is wrapped in a fixed harness — rate-limit → timeout → structured output → validate → ground → mock fallback. Failures never break the app; they fall back to the deterministic mock and log a warning. That makes the logs the primary signal: a rise in using mock fallback warnings while NIM_MOCK=false means NIM is unavailable or over quota.

WHY DEGRADE-AND-LOG The pairing is the design, not two independent features. Degrading gracefully means a NIM outage never becomes a broken ward — the board still populates from the deterministic mock, and a clinician’s workflow doesn’t stall on infrastructure they can’t see. But silent degradation is dangerous in its own way: the app would look healthy while quietly running on canned data, and nobody would know to fix the real thing. So every fallback leaves a trail. The warning line is the signal — the same event that keeps the app alive tells an operator that something upstream is wrong. Never break the app; always leave a trail. When both hold, the logs become a reliable early-warning system instead of a graveyard of swallowed errors.

The trap this avoids. A fallback with no log is the worst of both worlds: the app appears fine while running on mock data indefinitely, and the outage stays invisible until someone notices the extractions look generic. Watching using mock fallback in live mode turns that silent failure into a loud one.
02

Signals worth watching

A short list of what to look for, where it surfaces, and what it most likely means. Most of these read straight out of the logs.

HOW TO READ THIS Each row below is a symptom; the value is knowing what it points at and what to do about it. A signal that’s expected and self-correcting (rate-limit queueing) needs a different reaction from one that means an upstream dependency is down (the mock-fallback rise) or that the model itself is slipping (a climbing ungrounded rate). Read the table first, then the notes under it for the “so what.”

Signal Where it shows Likely meaning
using mock fallback warnings (live mode) AI-plane logs NIM outage, bad key, or quota exhausted.
timed out errors App / AI-plane logs Slow or half-open connection — 45s Next→AI, 30s AI→NIM bounds.
High ungrounded / dropped-barrier count ward extraction complete log ungrounded Model drift, or a note the grounding gate rejects.
Copilot refusals / grounded=false Copilot responses / logs Retrieval miss, or genuinely out-of-scope.
Rate-limit queueing AI-plane behaviour — token bucket, ~40 RPM headroom Bursts of extraction; expected and self-throttling.
failed count in the extraction summary runWardExtractionAction result + log Individual notes erroring — isolated, not fatal.

Reading each signal

using mock fallback in live mode

Why it matters: with NIM_MOCK=false the app is meant to run on the real model, so every fallback line means a live call failed and the deterministic mock answered instead. The app keeps working, which is precisely why this can go unnoticed — watching it is the whole point. What to do: check /healthz and the AI-plane logs. NIM is down, the key is bad, or you’re over quota. Extractions run on canned data until it clears.

timed out errors

Why it matters: the harness bounds each hop — 45s Next→AI, 30s AI→NIM — so a timeout is a call that ran past its budget, usually a slow or half-open connection rather than a hard error. What to do: a few under load is normal back-pressure. A sustained rise points at NIM latency or a degrading network path, and pairs with a mock-fallback rise as the timeouts fall back.

Climbing ungrounded rate

Why it matters: the grounding gate drops any extracted barrier it can’t tie back to the source note. A slow, steady climb in the ungrounded count on ward extraction complete is the clearest early sign of model drift — the model inventing detail the notes don’t support. What to do: sample the rejected items. If they’re genuine hallucinations, re-run evals and consider a prompt or model change.

Copilot refusals / grounded=false

Why it matters: a refusal is the copilot declining to answer rather than guessing — sometimes correct (the question is out of scope), sometimes a retrieval miss where the right context never reached the model. What to do: a low background rate is healthy caution. A spike suggests retrieval is failing to surface the relevant notes — worth checking against the embedding and reranker path.

Rate-limit queueing

Why it matters: the AI plane throttles itself to stay under the NIM quota (token bucket, ~40 RPM headroom). Queueing during a burst of extraction is the system working as designed, not an error. What to do: usually nothing — it self-throttles and drains. Persistent, growing queues mean sustained demand exceeds the quota; raise the limit or spread the load.

failed count in the extraction summary

Why it matters: each note is processed in isolation, so one bad note errors alone and the rest of the ward still lands — a non-zero failed is contained, not fatal. What to do: match the per-note note extraction failed line to see which note and why. A handful is normal; a large fraction of a run points at a systemic problem — malformed input, or the AI plane itself struggling.

03

In production

The proposed Azure deployment routes both container apps’ logs — plus Postgres, AI Foundry, and Front Door diagnostics — into Azure Monitor, Log Analytics, and Application Insights, with alerts on latency, error rate, and the AI eval gates.

Because the app already emits structured JSON, shipping to any collector — Application Insights, Loki, or otherwise — needs no call-site changes. Swap the sink in src/lib/logger.ts and the same log lines land wherever the platform wants them.

Where the signal lands

Azure Monitor, Log Analytics, and Application Insights collect both container apps’ logs alongside Postgres, AI Foundry, and Front Door diagnostics — one queryable place for the whole stack.

What it watches

Alerts fire on latency, error rate, and the AI eval gates, turning the same signals that live in logs today into thresholds someone gets paged on.

04

Gaps & next

What today’s picture doesn’t yet give you, and the concrete next step for each. All of it is tracked on the roadmap.

WHY THESE MATTER The gaps aren’t oversights — they’re the difference between seeing events and running a service. Logs tell you what happened; the missing pieces tell you how much, how fast, and how it moves over time, and they get someone paged before a clinician notices. Each one below buys a specific capability the log stream alone can’t give you.

No metrics

Per-call latency, token usage, and cost aren’t yet recorded — only the events, not the quantities around them. Buys you: the ability to answer “is it getting slower?” and “what is this costing?” — trends and budgets you can’t grep out of discrete log lines.

No distributed tracing

A request that crosses Next.js → AI plane → NIM has no correlated trace. Add OpenTelemetry spans around each hop to stitch a request together end to end. Buys you: when one extraction is slow or fails, a single trace id that follows it across all three planes — instead of hand-correlating timestamps across two log streams.

No alerting or dashboards

Signals live in logs, not on a board. Nothing pages an operator yet; you have to go looking. Buys you: the shift from reactive to proactive — a threshold on the mock-fallback rate pages someone the moment NIM goes down, rather than the outage surfacing when the extractions look generic.

Eval scores not tracked over time

The eval gates run, but their scores aren’t recorded run over run. Run them in CI and store the numbers to catch regressions early. Buys you: a quality trend line — you catch the build where grounding quietly dropped two points, instead of only seeing pass/fail on the current run.

05

Next steps

Today’s picture is a solid floor — structured logs, health and config surfaces, and degradation that always leaves a trail. The work ahead turns that stream of events into a service you can run without watching. In rough order of leverage:

OpenTelemetry tracing end to end

Spans around each hop of Next.js → AI plane → NIM, sharing one trace id, so a slow or failed extraction can be followed across all three planes instead of correlated by hand across two log streams.

Per-call token, cost & latency metrics

Record the quantities the logs only imply — how long each call took, how many tokens it burned, what it cost — so “is it getting slower?” and “what is this costing?” become charts, not guesses.

Dashboards & alerts

Lift the signals off the log tail and onto a board, with thresholds that page an operator — mock-fallback rate, error rate, and latency — the moment they cross, rather than when someone goes looking.

Eval scores tracked over time

Store each eval run’s scores so quality has a trend line, catching the build where grounding quietly slipped before it reaches production instead of only seeing pass/fail on the current run.

WHERE IT LIVES These are tracked, sequenced, and kept current on the Roadmap tab — head there for the full picture of what’s planned across the platform, not just monitoring.
