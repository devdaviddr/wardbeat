Product guide · Architecture

Architecture

Four cooperating planes behind a single front door, a stateless AI toolbox that never touches the database, and a fixed harness of guards wrapped around every model call.

● live on NVIDIA NIM Next.js 16 · FastAPI · Postgres/pgvector
01

System topology

WardBeat is built as four cooperating planes behind a single front door. The browser only ever talks to one of them — the Next.js experience layer — which is at once the front-end, the orchestrator of every AI workflow, and the single writer to the database. Behind it sit a stateless AI toolbox, the NVIDIA NIM inference models, and PostgreSQL. The design goal is simple: keep clinical data and control in one place, and make the AI plane something you can scale, test, and swap between hosted and on-prem models without touching the rest of the system.

Read this section as a set of decisions rather than a list of boxes. Each plane exists because giving it exactly one job — and denying it the others — is what makes the whole system easy to reason about, test, and deploy inside a hospital trust. The recurring move is the same one every time: concentrate authority (data, orchestration, control) in one plane, and keep the plane that talks to a language model as small, stateless, and replaceable as possible.

The four planes

Experience / BFF

Next.js 16

  • The only plane the browser talks to.
  • App Router, RSC, Server Actions — mutations are actions, not public API routes.
  • Edge proxy does route protection, role-based access control from a JWT claim (no DB at the edge), and a per-request nonce CSP plus HSTS and X-Frame-Options DENY.
  • The single database writer and the orchestrator of every AI workflow.
AI plane

FastAPI · Python 3.12

  • Small, stateless, internal-only — no database of its own.
  • A toolbox of NIM-backed primitives, never exposed to the browser.
  • Every endpoint except /health requires a shared x-service-token header.
  • Holds an in-process token-bucket rate limiter (~40 requests/min of NIM free-tier headroom); every capability degrades to a deterministic offline mock if NIM is unavailable.
Model plane

NVIDIA NIM

  • Self-hostable inference microservices behind an OpenAI-compatible API, authenticated with a bearer key.
  • Nemotron nano 9B — extraction, reasoning and narration chat.
  • nv-embedqa-e5-v5 — embeddings, 1024-dim.
  • llama-3.2-nv-rerankqa — rerank. The hosted free tier runs the demo; identical containers run on the trust’s own GPUs in production.
Data / knowledge

PostgreSQL 17 + pgvector

  • Single writer — Next.js, via Drizzle migrations.
  • Holds the ward domain and the AI outputs written back after each workflow.
  • Stores the policy knowledge base as vectors with an hnsw cosine index for nearest-neighbour search.

Why it matters — the two coloured borders that carry authority are the black Next.js plane (orchestration + the only write path) and the purple data plane (the one source of truth). The blue AI plane and the green model plane are deliberately powerless: they compute, they never decide and never persist. If you remember one thing about the topology, remember which boxes are allowed to change the world and which are not.

The AI plane is a stateless toolbox

Here is the key idea. The AI plane holds no state and never reaches the database — Next.js is the orchestrator and the only thing that touches Postgres. That single rule is the load-bearing decision of the whole architecture, so it is worth being precise about what it buys you.

Testability. Because every AI-plane endpoint is a pure function of its request — text in, structured JSON out, no hidden database read, no session, no prior turn remembered — you can test it the way you test any pure function. Give it a note, assert on the barriers; give it passages, assert on the answer. There is no fixture database to stand up, no state to reset between tests, and no “it passed yesterday” flakiness that comes from a service quietly accumulating state. A stateful AI service, by contrast, would force every test to reason about what happened before it.

Horizontal scale. Statelessness is also what lets you run ten copies of the AI plane behind a load balancer and route any request to any instance — none of them holds anything the next request depends on. The moment a service holds session or cache state that matters for correctness, you have to make requests sticky or share that state across instances, and scaling stops being free. Here it stays free: the only shared state in the system lives in one place, Postgres, and only Next.js talks to it.

Swapability. And because the plane is just a thin, uniform wrapper over model primitives — with no database schema of its own to keep in sync — you can replace the whole thing, or the models behind it, without the rest of the system noticing. The contract it exposes is a handful of HTTP endpoints, not a shared database, so there is no coupling to unpick.

So a Retrieval-Augmented-Generation query is not one big call to a black box; it is a short sequence that Next.js drives. Next.js calls /embed to turn the question into a vector, runs the pgvector nearest-neighbour search itself (that is where the database lives), calls /copilot/rerank to reorder the candidates, then calls /copilot/answer to compose a grounded, cited answer. The agent follows the same shape — Next.js retrieves the relevant policy from pgvector, then calls /agent/recommend — and so does forecasting, where Next.js gathers the features and calls the /forecast/* endpoints. Because the AI plane never holds state and never sees the database, it is easy to scale horizontally, easy to test in isolation, and trivial to swap between hosted and on-prem models.

Why retrieval lives in Next.js, not the AI plane. The obvious-looking design would be to send the question to the AI plane and let it do the whole RAG loop — embed, search, rerank, answer — in one call. WardBeat deliberately does not. The vector search runs in Next.js because that is where the database is, and the database is the one thing the AI plane is not allowed to touch. The AI plane only ever provides model primitives: turn this text into a vector, reorder these passages, compose an answer from those passages. Next.js keeps the retrieval — the step that reads clinical and policy data — on the same plane as every other data access, under the same single writer and the same access control. The common mistake this avoids is a second, shadow data path: an AI service that grows its own database connection, its own copy of the schema, and its own idea of who is allowed to read what.

Next.js is the single writer and the orchestrator

The mirror image of the stateless AI plane is that Next.js is the only plane that writes to Postgres, and the only plane that orchestrates a workflow end to end. This is a deliberate choice, not an accident of where the code happened to live. When exactly one process owns every write, there is one source of truth for what is on the board, one place where a transaction either fully happens or fully does not, and one place to reason about ordering and consistency. If the AI plane could also write — say, persist an extraction directly — you would have split-brain writes: two processes racing to update the same encounter, each with its own view of “latest wins”, and no single transaction boundary around the pair. That is the class of bug that produces a board showing barriers from a note that was already superseded. Concentrating writes in the orchestrator removes the race by construction. The AI plane returns a result; Next.js decides whether, when, and how to persist it.

Why it matters — “single writer” is not about performance, it is about not having to trust two processes to agree. The AI plane can be restarted, scaled, or swapped mid-workflow without any risk to data integrity, precisely because it never held the pen.

The AI plane’s API

Every capability is one internal HTTP call. The browser never sees these; only Next.js calls them, over the private network, with a shared service token. The shape of this table is itself the argument: each row is a self-contained model primitive with no memory of the last row, which is exactly what makes the plane stateless and swappable. Note, too, where the LLM is used and where it is deliberately not — the /forecast/* rows that compute numbers use no language model at all.

02

The AI flow

The guiding rule runs through every capability below: generative AI does only the language and the reasoning, and deterministic code does the forecasting and holds the data. A language model reads a note into structured data, decides how to route a question, drafts a grounded action, and narrates a briefing — but it never computes a probability, queries the database, or takes an action on its own. The four pipelines that follow are the whole of WardBeat’s AI, each one a short sequence Next.js drives, each one ending in something a clinician can verify or a gate a human controls.

1 · Barrier extraction — reading notes into data

The job: turn free-text ward notes into structured, board-ready barriers — without letting the model invent any of them. A creative read is welcome; an unverified claim is not. Uses temperature 0, structured output / JSON mode, grounding, and a deterministic fallback.

1

Model reads, code constrains

The note text goes to Nemotron at temperature 0 in JSON mode, bounded by a configurable max_tokens, and the model returns strict JSON. Determinism here means the same note yields the same read.

2

Sanitise the raw output

Code enforces a five-barrier-type allow-list, drops empty verbatim quotes, and defaults missing confidence to 80. Anything the model returns that is off-schema simply does not survive this step.

3

The grounding gate

For every barrier, its verbatim quote is searched back in the source note — an exact case-insensitive match first, then a fuzzy sliding-window match at ≥0.75 similarity — and snapped to real character offsets. A quote that cannot be located means the barrier is deleted and the result is flagged ungrounded.

4

Only grounded barriers persist

What reaches the board is exactly the set that survived the gate, each linked to its source sentence so a clinician can click through to the evidence. If the model is off or fails outright, a deterministic keyword extractor takes over.

The point — the model may be creative about reading, but every claim is mechanically verified against the source before anyone sees it; a hallucinated barrier physically cannot reach the board.

2 · Copilot — the right retrieval for each kind of question

The job: answer two very different kinds of question — “what is happening on my ward right now?” and “what does policy say?” — each with the retrieval it actually needs. Two data shapes, two tools. Uses structured output, embeddings, vector search, RAG, reranking, and grounded citation.

1

Classify the question

A first pass decides whether the question is about ward_state, about policy, or out_of_scope. That single decision routes everything downstream.

2

Ward-state → validated filter

The model translates the question into a small, validated JSON filter like {mffd:true, barrier:"transport"}, sanitised against an allow-list and run over the board data. The model chooses what to filter, never how to query — no SQL, no database access — and the matching beds light up.

3

Policy → genuine RAG

The question is embedded and the policy passages are vector-searched by meaning in pgvector, then the shortlist is reranked with a sharper model to surface the most relevant few.

4

Answer from evidence, or refuse

The model answers from only the numbered passages, citing each one it used — or it returns grounded:false and refuses (“I don’t have policy that covers that”). Weak support becomes a refusal, not a guess.

The point — structured data gets a validated filter; unstructured data gets vector RAG; both paths end the same way, by citing evidence or admitting there is none.

3 · Action recommender — a narrow, human-gated agent

The job: given a patient’s barriers, propose the next concrete step for each — grounded in policy, capped to a safe menu, and never acting on its own. Retrieve, then reason, then hand to a human. Uses agents & tools, retrieval, and grounding.

1

Retrieve the relevant policy

A tool call into pgvector pulls the policy passages that bear on this patient’s barriers — the agent gathers evidence before it reasons.

2

Reason over barriers plus policy

The model proposes exactly one action per barrier from a closed allow-list — chase TTOs, book transport, arrange social care, escalate a review, or other — each with a one-sentence rationale grounded in cited policy and a priority of 1–3. Off-menu actions are coerced to a safe default.

3

Recommend only — a human decides

Nothing acts autonomously. A person Approves or Dismisses each recommendation; approving marks the barrier in progress and writes an audit row. Nothing is ever sent to pharmacy or transport.

The point — autonomy is capped by design: a fixed action menu, mandatory policy grounding, and a human gate on every single recommendation.

4 · Forecast & narrate — the deliberate absence of an LLM

The job: predict discharge likelihood and demand, then explain it in plain language — while keeping the model as far from the arithmetic as possible. The numbers are calculated; only the prose is generated. Uses the discipline of knowing when not to use an LLM.

1

Numbers from a transparent model

A deterministic logistic model with readable, monotone weights produces the figures: being medically fit pushes discharge odds up, while each open barrier and a slow social-care package pushes them down, combined into a probability. Demand is a documented baseline. No language model touches any figure — it is inspectable and unit-tested.

2

Narrate, don’t recompute

The finished numbers go to the model with one instruction: write a 2-to-4-sentence briefing using exactly these numbers, never inventing or recomputing one. The model does the language; the model never does the maths.

The point — asking an LLM to predict a length-of-stay would be the anti-pattern (unaccountable, unfalsifiable); splitting the calculable part (a testable model) from the linguistic part (narration) is the lesson made concrete.

03

The model-call harness

The four pipelines above each reach a language model exactly once or twice — but the prompt is the smallest part of what happens. Every single model call in WardBeat is wrapped in the same fixed sequence of guards, and most of the reliability comes from that wrapper, not from the words sent to the model. The harness runs the same way whether the caller is extraction, the copilot, or the agent: acquire a token, bound the call in time, force structured output, re-validate it in code, ground it against the source, and — if anything is off or fails — degrade to a deterministic mock so the endpoint always returns something usable.

1

Rate limit

The AI plane holds an async token-bucket limiter sized to about 40 requests a minute — headroom under the NIM free tier. A call has to acquire a token before it can reach a model, so a burst of extractions queues politely instead of tripping the provider’s limit.

2

Timeout

The Next.js→AI-plane call is bounded by a 45-second abort timeout, and the AI-plane→model call by a 30-second one. A stalled connection cannot wedge a batch — the timeout fires, the call fails cleanly, and the fallback takes over.

3

Structured output

The model runs at temperature 0 with JSON mode (response_format: json_object) so output is repeatable and machine-readable. A tolerant parser extracts the first {...} block even if the model wraps its JSON in prose, so a chatty preamble never breaks the call.

4

Validate

The parsed JSON is re-checked in code against allow-lists — barrier types, action types, intent fields. The model’s field names and values are never trusted as-is; unknown values are coerced to safe defaults or dropped entirely.

5

Ground

Extracted claims are matched back to their source — a quote is located in the note, an answer must cite a retrieved passage — and anything that cannot be tied to evidence is dropped or refused. This is the same grounding gate the pipelines depend on, applied uniformly.

6

Mock fallback

If the model backend is disabled by a flag, is unavailable, or any step above raises, the call degrades to a deterministic offline mock that returns the same shape of result. The endpoint always returns something usable, and the app never hard-breaks.

The prompt is the smallest part. Blue boxes are the AI-plane guards, green is the model call itself, and teal is the code that verifies whatever the model returned. The model is trusted to be creative inside a fixed cage — and everything outside the green box is plain, testable code that runs the same way every time.
04

Request lifecycle

Take a single Run extraction request — a clinician asks WardBeat to read a ward note and pull out the discharge barriers. It crosses all four planes and returns to Postgres, with Next.js in control the whole way, and the harness from the previous section wrapping the model call in the middle.

The point of walking it hop by hop is that every hop earns its place — none of them is there for tidiness. Each boundary crossing is a place where trust is checked or authority is handed over, and reading them in order is the clearest way to see why the topology is shaped the way it is. Notice as you go how the arrows narrow: the browser can reach exactly one plane, that plane can reach the AI plane and the database, and the AI plane can reach only the model. Authority decreases the further you get from the front door.

1

The browser asks Next.js — and nothing else

The clinician triggers a Server Action. The request passes the edge proxy, which checks the JWT session and role before the work begins — this is the outermost trust boundary, and it is on the hot path so an unauthenticated or under-privileged request is rejected before any expensive work runs. No API route is exposed; the browser cannot reach the AI plane, NIM or Postgres. Why this hop exists: a single front door means there is exactly one surface to authenticate, authorise, and apply the CSP to. Every other plane can therefore assume its caller is already trusted.

2

Next.js calls the AI plane over the private network

Next.js sends the note text to /extract on the internal-only AI plane, carrying the shared x-service-token header. This hop never leaves the internal network. Why this hop exists: the AI plane is a second, internal trust boundary — it refuses any request without the service token, which is what lets it stay simple and unauthenticated-by-user while still never being reachable from outside. The browser has no route to it and no token to present even if it did.

3

The AI plane calls NIM — inside the harness

The AI plane forwards the prompt to Nemotron over the OpenAI-compatible NIM API in JSON mode at temperature 0, authenticated with a bearer key and shaped by its token-bucket rate limiter and timeout. If NIM is unavailable, it degrades to a deterministic offline mock.

4

The model returns structured output

Nemotron returns grounded barriers, an estimated discharge date and the medically-fit-for-discharge flag. The AI plane parses, validates and grounds the result, then hands it back — holding no state of its own.

5

The result flows back to Next.js

Next.js receives the validated result. All orchestration — retries, validation, deciding what to persist — lives here, not in the AI plane.

6

Next.js — and only Next.js — writes to Postgres

The extracted barriers and flags are written to PostgreSQL through the pooled Drizzle client. The AI plane never touched the database; the single writer is the front door. Why this hop closes the loop: the write is the one irreversible act in the whole request, and it happens in the plane that has been in control since step 1 — so the same process that authenticated the clinician is the one that decides what lands on the board, inside one transaction. There is no second writer to disagree with.

Why it matters — six hops, three trust boundaries: the edge (is this clinician allowed?), the service token (is this caller the orchestrator?), and the model’s bearer key (is this the AI plane?). Trust is re-established at each crossing rather than assumed once, so compromising one plane does not hand an attacker the next.

Trust boundaries, made explicit

Three concentric boundaries do the security work, and it is worth naming each and the failure it prevents.

The browser only ever talks to Next.js

There is no public API route and no client-side call to the AI plane, NIM, or Postgres. This collapses the attack surface to a single authenticated front door — the thing you would otherwise have to defend in three places you now defend in one.

Edge: per-request nonce CSP + RBAC

The proxy applies role-based access control from a JWT claim (no database read at the edge, so it stays fast) and a Content-Security-Policy carrying a fresh per-request nonce. The nonce means an injected inline script has no valid nonce and simply will not run — it turns the whole class of XSS-via-injected-<script> into a non-event, rather than relying on catching every injection point.

The AI plane is internal-only and token-gated

Every endpoint but /health demands the shared x-service-token, and the plane is never published to the internet. Even if an attacker reached the internal network, they would still need the token; even with the token, they reach a plane that holds no data and cannot write. Defence in depth, not a single wall.

The model plane is reached only by bearer key

NIM sits behind an OpenAI-compatible API authenticated with a bearer key that only the AI plane holds. The models are a leaf: they compute and return, and have no path back to the browser, the orchestrator, or the database.

Deployment & data residency

The same lifecycle runs identically in the hosted demo and on-prem. The whole stack ships from Docker: in production docker-compose.prod.yml puts a Cloudflare Tunnel in front as the public gateway — there is no inbound port — routing to app:3000 (Next.js), which talks to db:5432 (Postgres) and minio:9000 for uploads, with the AI plane as its own pinned image and every container running as a non-root user.

Going on-prem is a config change — swap the NIM base URL and key — not a rewrite, and this is a bigger claim than it sounds. The reason it holds is the OpenAI-compatible contract: the AI plane speaks to NIM through the same request and response shape whether the models run on NVIDIA’s hosted free tier or on the trust’s own GPUs, so moving from one to the other changes two environment values and nothing else. Because the container image, the schema, the orchestration, and every guard in the harness are identical across both, there is no fork of the codebase to maintain and no “on-prem edition” that drifts from the demo. That is precisely what keeps clinical data inside the trust’s own walls without a second, divergent build: the data-residency guarantee is a deployment setting, not a rewrite, and the thing you tested in the demo is bit-for-bit the thing that runs in the hospital.

The lesson made concrete. When the boundary between “what changes on-prem” and “what stays the same” is a config file rather than a code branch, going into a trust is a procurement conversation, not an engineering project — and the clinical safety you proved once is the clinical safety that ships.
05

Data & knowledge

The AI plane holds nothing; all of it lands here. WardBeat keeps everything in a single PostgreSQL 17 database with the pgvector extension. Next.js is the only writer — schema and migrations are defined once, in TypeScript, through Drizzle ORM. That one database holds three kinds of data — the ward domain, the AI outputs, and the policy knowledge base — sitting right alongside the platform and identity tables. There is no separate vector database to run: the policy vectors live in the same Postgres as the relational ward data.

The data model

Because the relational ward data and the policy vectors share one Postgres via pgvector, there is no separate vector database to operate, and the vectors sit transactionally beside the data they relate to. For a corpus this size, that is the deliberate simplicity choice — one database to back up, one place where consistency is guaranteed.

From note to audited action

1

A note is written

A nursing note lands as a row in notes — the free-text ward-round or nursing entry that everything downstream is grounded in.

2

Extraction runs

A row is written to aiExtractions (the raw model output, with the model name) and grounded rows to barriers. Each barrier cites a character span back in the note — and only barriers whose quote was located in the note are stored.

3

Encounter status is updated

The patient’s encounters row is denormalised with the current MFFD flag and estimated discharge date. Latest note wins.

4

The agent recommends

The agent turns each barrier into one or more recommendations rows — action type, rationale, priority and citations — grounded in retrieved policyChunks.

5

A human approves

On approval an actionAudit row records who approved or dismissed which recommendation and when, and the barrier is marked in progress. Nothing acts on external systems.

How the policy knowledge base is built

Retrieval works by meaning, not keywords. A policy document is split into passages, each passage is embedded into a 1024-dim vector by the NVIDIA embedding model, and text plus vector are stored in policyChunks behind an hnsw cosine index. At query time the question is embedded the same way and pgvector finds the nearest chunks by cosine similarity. One subtlety matters: NVIDIA embedding models are asymmetric — passages are embedded with input_type passage and questions with input_type query, so the stored corpus and the incoming question land in the same space and match correctly.

06

Next steps

The architecture you have just read is deliberately the simplest thing that keeps clinical data in one place and every model call in a cage. That simplicity is a starting point, and a few of its edges are where the design grows next — each one an extension of a decision made above, not a reversal of it.

A shared rate-limit store for scale-out

Today the AI plane’s token bucket and the app’s rate limiter are in-memory — correct and fast for a single instance. The moment you run several instances behind a load balancer, each holds its own counter and the effective limit multiplies. The fix is small precisely because the planes are already stateless: move the limiter to a shared store (Redis) so every instance draws from one bucket. The topology does not change; one piece of state moves out of process.

OpenTelemetry tracing across the hops

The six-hop lifecycle is easy to narrate on paper; in production you want to see a single request cross the browser → Next.js → AI plane → NIM → Postgres path as one trace, with timing on each boundary. Propagating a trace context across the hops turns the diagram in section 4 into a live, per-request waterfall — invaluable the first time a model call is slow and you need to know which hop owns the latency.

Shipping the Azure design

The Docker + Cloudflare Tunnel deployment is the on-prem-friendly baseline. The Azure design maps the same four planes onto managed services — Container Apps, a managed Postgres with pgvector, private networking — for trusts that prefer a cloud landing zone. Because the contract between planes is HTTP and a shared database, the mapping is a hosting decision, not an architectural one.

Where the AI plane goes

Everything that makes the plane stateless and swappable is what makes model upgrades routine: a newer Nemotron, a stronger reranker, or on-prem GPUs are all a config change behind the same endpoints. The harness and grounding gates stay exactly where they are — new models are dropped into the same cage, not trusted more.

Why it matters — none of these is a rewrite. Each is a small change enabled by a decision already made: statelessness makes the shared limiter easy, single-writer makes tracing legible, and the OpenAI-compatible contract makes the hosting target interchangeable. Good architecture is the one whose next steps are cheap.
