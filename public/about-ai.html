How WardBeat uses AI

Generative AI does exactly one thing here — language and reasoning. The numbers, the retrieval, and the guards around every call are plain, testable code.

● live on NVIDIA NIM Nemotron · nv-embedqa · nv-rerankqa
01

The four capabilities

WardBeat draws a hard line down the middle of the product. Generative AI is trusted with language and reasoning only — reading a note into structured data, answering a question from retrieved sources, proposing a next step, turning finished numbers into prose. Everything else — computing a forecast, holding and filtering data, verifying a claim against its source — is deterministic code that runs the same way every time. The four pipelines below each cross that line exactly where it belongs, and never further.

The pattern is the same each time: let the model be creative inside a fixed cage, then verify whatever it returned with code before anyone sees it. A hallucinated barrier, an ungrounded answer, or an off-menu action physically cannot reach a clinician.

1 · Barrier extraction — reading notes into data

The job: turn free-text ward notes into structured, board-ready barriers — without letting the model invent any of them. A creative read is welcome; an unverified claim is not.

Reading a nurse’s free-text note into a tidy list of discharge barriers is a genuinely linguistic task — the same blocker gets written a dozen different ways, and no set of keyword rules catches them all. That is exactly the kind of work a language model is good at, so we let one do it. The discipline is in how we let it: a small model (nothing here needs a frontier one), pinned to temperature 0 so the same note always reads the same way, forced into strict JSON so the output is data rather than prose — and then, crucially, every claim it makes is checked back against the note before anyone sees it. The diagram below is that pipeline, left to right.

Why temperature 0 + strict JSON — temperature is the model’s “creativity dial”; turned to zero it stops sampling and always picks its most-likely next token, so extraction becomes reproducible and auditable — run the same note twice, get the same barriers. JSON mode makes the output a machine-readable object instead of a paragraph we would have to parse with fragile regexes. Without both, the same note could yield different barriers on Monday and Tuesday, and a chatty model could break the parser mid-shift.

1

Model reads, code constrains

The note text goes to Nemotron at temperature 0 in JSON mode, bounded by a configurable max_tokens, and the model returns strict JSON. Determinism here means the same note yields the same read.

2

Sanitise the raw output

Code enforces a five-barrier-type allow-list, drops empty verbatim quotes, and defaults missing confidence to 80. Anything the model returns that is off-schema simply does not survive this step.

3

The grounding gate

For every barrier, its verbatim quote is searched back in the source note — an exact case-insensitive match first, then a fuzzy sliding-window match at ≥0.75 similarity — and snapped to real character offsets. A quote that cannot be located means the barrier is deleted and the result is flagged ungrounded.

4

Only grounded barriers persist

What reaches the board is exactly the set that survived the gate, each linked to its source sentence so a clinician can click through to the evidence. If the model is off or fails outright, a deterministic keyword extractor takes over.

The point — the model may be creative about reading, but every claim is mechanically verified against the source before anyone sees it; a hallucinated barrier physically cannot reach the board.

The grounding gate is the whole game. A barrier that the model invents — a plausible-sounding blocker that was never in the note — is the one failure a clinician must never see. The gate makes that impossible by construction: the model must quote the exact words it based each barrier on, and code then searches for that quote back in the source note (an exact match first, then a fuzzy sliding-window match at ≥0.75 similarity to forgive minor paraphrasing). If the quote cannot be found, the barrier is deleted, not shown with a warning. Think of it like a footnote a fact-checker refuses to publish unless they can point at the exact sentence it came from. In healthcare you do not ask people to trust the model — you show them the evidence, and drop anything you cannot back up.

2 · Copilot — the right retrieval for each kind of question

The job: answer two very different kinds of question — “what is happening on my ward right now?” and “what does policy say?” — each with the retrieval it actually needs. Two data shapes, two tools.

A tempting shortcut would be to point the model at everything and let it figure out how to fetch what it needs. We deliberately do not. The two kinds of question have completely different data underneath — the ward’s live state is structured rows in a database, while policy is unstructured prose — and the right retrieval for each is different. So a classifier routes the question first, and each branch uses a purpose-built tool that the model is not allowed to step outside of. Follow the split below.

Why the model never writes SQL — on the ward-state path the model only chooses what to filter (a small JSON object like {mffd:true, barrier:"transport"}), validated against an allow-list of fields; it never chooses how to query and it never touches the database. If the model could emit SQL, a hallucinated or manipulated query could read or delete data it should never see — the classic prompt-injection-to-database hole. Restricting it to a validated filter means the worst it can do is ask for a combination that returns nothing.

1

Classify the question

A first pass decides whether the question is about ward_state, about policy, or out_of_scope. That single decision routes everything downstream.

2

Ward-state → validated filter

The model translates the question into a small, validated JSON filter like {mffd:true, barrier:"transport"}, sanitised against an allow-list and run over the board data. The model chooses what to filter, never how to query — no SQL, no database access — and the matching beds light up.

3

Policy → genuine RAG

The question is embedded and the policy passages are vector-searched by meaning in pgvector, then the shortlist is reranked with a sharper model to surface the most relevant few.

4

Answer from evidence, or refuse

The model answers from only the numbered passages, citing each one it used — or it returns grounded:false and refuses (“I don’t have policy that covers that”). Weak support becomes a refusal, not a guess.

Why “answer only from retrieved passages, or refuse” — the policy path is genuine RAG: the question is embedded, matched against policy by meaning in pgvector, and the shortlist reranked so the best few passages surface. The model is then told to answer using only those numbered passages and to cite each one — or, if they do not actually cover the question, to return grounded:false and say so. This is what stops the confident-but-wrong answer: a general-purpose model asked “what’s the escalation policy for a delayed transfer?” will happily invent a reasonable-sounding one from its training data. Forcing it to cite retrieved trust policy — or refuse — means a weak match becomes an honest “I don’t have policy that covers that,” which on a ward is far safer than a plausible fabrication.

The point — structured data gets a validated filter; unstructured data gets vector RAG; both paths end the same way, by citing evidence or admitting there is none.

3 · Action recommender — a narrow, human-gated agent

The job: given a patient’s barriers, propose the next concrete step for each — grounded in policy, capped to a safe menu, and never acting on its own. Retrieve, then reason, then hand to a human.

This is the one capability that looks like an “agent” in the buzzword sense — it retrieves, reasons, and produces a plan of action. So it is also where the safety design has to be strictest. The reasoning is real and useful, but three hard constraints wrap it: the model may only pick from a fixed allow-list of actions, it may only recommend (never execute), and every proposal passes a human gate that writes an audit row. Trace the flow below, then read why each constraint is there.

Why a fixed action allow-list — the model chooses one action per barrier from a closed menu (chase TTOs, book transport, arrange social care, escalate a review, or “other”), and anything off-menu is coerced to a safe default. An open-ended agent that can “take any action it deems appropriate” cannot be tested, reasoned about, or trusted near patients — you cannot enumerate what it might do. A closed menu means the set of possible outputs is small, reviewable, and safe by construction; the model’s cleverness is spent on which known-safe step fits, not on inventing new ones.

1

Retrieve the relevant policy

A tool call into pgvector pulls the policy passages that bear on this patient’s barriers — the agent gathers evidence before it reasons.

2

Reason over barriers plus policy

The model proposes exactly one action per barrier from a closed allow-list — chase TTOs, book transport, arrange social care, escalate a review, or other — each with a one-sentence rationale grounded in cited policy and a priority of 1–3. Off-menu actions are coerced to a safe default.

3

Recommend only — a human decides

Nothing acts autonomously. A person Approves or Dismisses each recommendation; approving marks the barrier in progress and writes an audit row. Nothing is ever sent to pharmacy or transport.

Recommend-only, human gate, audit trail. Nothing the agent produces acts on the world. It writes no orders, sends nothing to pharmacy or transport, and moves no patient — it only surfaces a proposal with a cited rationale. A person Approves or Dismisses each one; approving is what marks the barrier in progress, and every decision writes an audit row recording who decided what and when. Two things fall out of this. First, accountability stays with a clinician, where it legally and ethically belongs — the AI advises, a human decides. Second, the audit trail turns the whole feature into a dataset: over time you can see which recommendations get approved and which get thrown out, which is the honest way to measure whether the agent is any good — and, later, to improve it.

The point — autonomy is capped by design: a fixed action menu, mandatory policy grounding, and a human gate on every single recommendation.

4 · Forecast & narrate — the deliberate absence of an LLM

The job: predict discharge likelihood and demand, then explain it in plain language — while keeping the model as far from the arithmetic as possible. The numbers are calculated; only the prose is generated.

This pipeline is the sharpest illustration of the whole thesis, because it is defined by what the LLM is not allowed to do. A discharge probability is a number a clinician acts on, so it has to be calibrated, testable, and identical for identical inputs. Those are exactly the properties a language model cannot offer. So the calculable part and the linguistic part are split down the middle: a small, transparent statistical model does every figure, and the LLM is handed the finished numbers and asked only to read them aloud in a sentence or two. Watch where the boxes change colour below — that is where the model is and is not.

Why the numbers are a deterministic model, not an LLM — the forecast is a plain logistic model with a handful of readable, monotone weights: being medically fit pushes discharge odds up, each open barrier and a slow social-care package pushes them down. Because it is ordinary arithmetic it is inspectable (you can read exactly why a patient scored 0.62), testable (unit tests pin the output for known inputs) and calibratable (weights can be re-fit against real length-of-stay history). An LLM asked to “predict the discharge probability” gives you a number with none of those properties — unfalsifiable, non-reproducible, and impossible to honestly unit-test. This is the clearest case in the product of when not to use an LLM.

1

Numbers from a transparent model

A deterministic logistic model with readable, monotone weights produces the figures: being medically fit pushes discharge odds up, while each open barrier and a slow social-care package pushes them down, combined into a probability. Demand is a documented baseline. No language model touches any figure — it is inspectable and unit-tested.

2

Narrate, don’t recompute

The finished numbers go to the model with one instruction: write a 2-to-4-sentence briefing using exactly these numbers, never inventing or recomputing one. The model does the language; the model never does the maths.

Why the LLM only narrates — narration is a language task (turn “0.62 · 3 days · one open barrier” into a readable briefing), and there the model earns its place. But it is handed the finished figures with one rule: use exactly these numbers, never invent or recompute one. Keeping the model downstream of the maths means the sentence a clinician reads and the number it describes can never disagree — and both halves stay independently auditable and testable.

The point — asking an LLM to predict a length-of-stay would be the anti-pattern (unaccountable, unfalsifiable); splitting the calculable part (a testable model) from the linguistic part (narration) is the lesson made concrete.

02

The model-call harness

The four pipelines above each reach a language model exactly once or twice — but the prompt is the smallest part of what happens. Every single model call in WardBeat is wrapped in the same fixed sequence of guards, and most of the reliability comes from that wrapper, not from the words sent to the model. The harness runs the same way whether the caller is extraction, the copilot, or the agent: acquire a token, bound the call in time, force structured output, re-validate it in code, ground it against the source, and — if anything is off or fails — degrade to a deterministic mock so the endpoint always returns something usable.

It helps to read the six guards not as a checklist but as six specific failures we refuse to let happen. Each one exists because of a concrete way a naïve “just call the model” endpoint breaks in production — and the model call itself, the green box in the middle, is a small slice of the whole. Here is the failure each guard prevents.

Rate limit → provider lock-out

An async token bucket (~40 req/min) means a burst of extractions queues politely instead of slamming the provider and getting the whole app throttled or 429-blocked mid-shift.

Timeout → a wedged batch

Every call is bounded (45s at the edge, 30s at the model). Without it, one stalled connection hangs a request forever and can back up an entire batch of notes behind it.

Structured output → an unparseable blob

Temperature 0 + JSON mode make the output repeatable and machine-readable; a tolerant parser pulls the first {…} even out of a chatty preamble, so a wordy model never breaks the caller.

Validate → an off-schema value

The parsed JSON is re-checked against allow-lists in code. The model’s field names and values are never trusted as-is — unknown ones are coerced to a safe default or dropped, so a novel label cannot corrupt the board.

Ground → a hallucination

Claims are matched back to their source — a quote located in the note, an answer tied to a retrieved passage — and anything unverifiable is dropped or refused. This is the anti-fabrication step, applied uniformly.

Mock fallback → a hard failure

If the backend is flagged off, unavailable, or any step raises, the call degrades to a deterministic offline mock returning the same result shape. The endpoint always returns something usable; the app never hard-breaks.

Why the wrapper, not the prompt, does the work — a prompt is a request, not a guarantee: models ignore instructions, drift, stall, and occasionally invent. Every guard above is code that runs regardless of what the model did, so the endpoint’s safety and reliability do not depend on the model behaving. That is what lets us trust a small model in a clinical setting — we do not trust the model, we trust the cage around it.

1

Rate limit

The AI plane holds an async token-bucket limiter sized to about 40 requests a minute — headroom under the NIM free tier. A call has to acquire a token before it can reach a model, so a burst of extractions queues politely instead of tripping the provider’s limit.

2

Timeout

The Next.js→AI-plane call is bounded by a 45-second abort timeout, and the AI-plane→model call by a 30-second one. A stalled connection cannot wedge a batch — the timeout fires, the call fails cleanly, and the fallback takes over.

3

Structured output

The model runs at temperature 0 with JSON mode (response_format: json_object) so output is repeatable and machine-readable. A tolerant parser extracts the first {...} block even if the model wraps its JSON in prose, so a chatty preamble never breaks the call.

4

Validate

The parsed JSON is re-checked in code against allow-lists — barrier types, action types, intent fields. The model’s field names and values are never trusted as-is; unknown values are coerced to safe defaults or dropped entirely.

5

Ground

Extracted claims are matched back to their source — a quote is located in the note, an answer must cite a retrieved passage — and anything that cannot be tied to evidence is dropped or refused. This is the same grounding gate the pipelines depend on, applied uniformly.

6

Mock fallback

If the model backend is disabled by a flag, is unavailable, or any step above raises, the call degrades to a deterministic offline mock that returns the same shape of result. The endpoint always returns something usable, and the app never hard-breaks.

The prompt is the smallest part. Blue boxes are the AI-plane guards, green is the model call itself, and teal is the code that verifies whatever the model returned. The model is trusted to be creative inside a fixed cage — and everything outside the green box is plain, testable code that runs the same way every time.
03

The models

The guiding rule is to use generative AI where it belongs and no further. Language models do the language: reading notes into structured data, answering questions from retrieved sources, and turning numbers into prose. Everything numeric or safety-critical stays in plain, testable code. The choices below follow from two constraints: clinical data should be able to stay inside the hospital, and quality has to be measurable.

Why NVIDIA NIM — the platform choice is driven by data sovereignty. A hosted frontier API is the easy default, but it means patient data leaves the hospital trust, which is a non-starter in healthcare. NIM ships the models as self-hostable microservices behind an OpenAI-compatible API: the demo runs on the hosted free tier, and moving to production is a config change — the same client code points at NIM containers running on the hospital’s own GPUs, so the data never leaves the building. OpenAI-compatibility also means no lock-in — the client is standard and any model can be swapped. Raw self-hosting with vLLM would work too, but then you rebuild serving, optimisation, embedding and reranking yourself; NIM is the middle path.

The three models

Each model is the smallest one that does its job well. Nothing here needs a frontier model, and a smaller model is faster, cheaper, and easier to run on-prem.

Why the smallest model that does the job — the reflex to reach for the biggest, smartest model is the wrong one here. None of these tasks — reading a note into JSON, routing a question, narrating finished numbers — needs frontier-level reasoning; they need reliability, and the harness supplies that. Choosing the smallest model that clears the bar pays off three times over: it is cheaper (extraction runs on every note), faster (lower latency per call), and far easier to run on-prem — a 9B model fits on hardware a hospital can realistically own, where a frontier model would not. Right-sizing each model is what makes the sovereignty story practical rather than aspirational.

Every capability has a deterministic offline stand-in. With no API key, or one flag flipped, the whole system runs with no model at all — and a failed live call falls back to the mock rather than breaking the app.

04

When not to use an LLM

The most important AI decision in WardBeat is where the AI stops. Discharge probability and bed demand are numbers a clinician acts on — they have to be calibrated, testable, and the same for the same inputs. A language model is the wrong tool for that: it is unaccountable and unfalsifiable, and there is no honest way to unit-test a figure it invents. So the calculable part and the linguistic part are split cleanly. A small, transparent statistical model with readable weights computes every figure; the LLM is handed the finished numbers and asked only to narrate them in a sentence or two, forbidden from inventing or changing a single one.

When not to use a language model. Discharge probability and bed demand come from a small, transparent statistical model with readable weights, not the LLM. Numbers have to be calibrated and testable; the LLM only narrates them, and is forbidden from inventing or changing a figure. Knowing where to stop using AI is part of the design.
05

Next steps

The design above is deliberately conservative — the cage first, cleverness second. That same foundation is what makes the next moves safe to add, because each one slots into the existing harness rather than working around it. Here is where the AI goes from here.

NeMo Guardrails

Add a declarative guardrail layer in front of the copilot and agent — programmable rails for topic boundaries, jailbreak resistance, and output policy. It formalises, in one place, the input/output checks the harness does today by hand.

Streaming responses

Stream the copilot and narrator token-by-token so answers appear as they are written. The grounding and citation checks still run on the completed output — streaming changes the delivery, never the verification.

Per-capability model choice

Because the client is OpenAI-compatible, each capability can point at the model that suits it — a stronger reasoner for the agent, a leaner one for routing — chosen by measured quality, not by defaulting everything to one model.

Active learning from the audit trail

Every approved or dismissed recommendation is already an audit row. That is a labelled dataset waiting to be used — to measure which suggestions clinicians trust, tune prompts and weights against real decisions, and improve the model where it matters.

The through-line — none of these loosens the guarantees; each one is added inside the harness, so the same rules — validate, ground, human-gate, fall back — still hold. The model gets more capable; the cage stays.
