Evaluating the AI

AI quality in WardBeat is a number, not a feeling — every capability has a labelled dataset, a metric that fits the task, and a hard gate that runs against the live models.

● live on NVIDIA NIM four eval harnesses · hard gates · release-blocking
01

How quality is proven

AI quality here is a number, not a feeling — measured, not guessed. Every AI capability has a labelled synthetic dataset, a metric that fits the task, and a hard gate; the harnesses run against the live NVIDIA NIM models and exit non-zero when a gate is missed, so they double as a release gate. This is the concrete form of the project’s thesis — we don’t trust the model, we measure it.

Why evaluate an AI system at all

A traditional function is deterministic — the same input gives the same output, and a handful of unit tests pin it forever. A language model is not. It is probabilistic: two calls with the same prompt can return different text, and its behaviour drifts as prompts, model versions, or upstream weights change underneath you. That means a demo that “looks right” proves nothing — it is one lucky sample, not evidence. The only honest way to know whether the AI is good enough to ship is to turn quality into a measured number, run against a known-answer dataset, and hold it to a threshold you agreed on in advance.

Why this matters Without a number, “is the AI working?” has no answer but a vibe — and vibes ship regressions. A model can silently get worse and still feel fine on the three examples you happen to click. The eval harness replaces that feeling with a figure and a pass/fail line.

The thesis. Three layers of testing prove it, from the bottom up: deterministic unit tests pin the non-AI logic and the AI-plane contract, the eval harnesses score the live models against planted ground truth, and a single mock ↔ live flag keeps the system behaving identically offline and on real models.

The three layers of testing

Layer Tooling What it proves
Deterministic unit tests Vitest · pytest The non-AI logic and the AI-plane contract behave and don’t leak secrets.
AI eval harnesses pnpm eval:* The live models hit their accuracy, grounding, and ranking gates.
Mock ↔ live parity NIM_MOCK flag The system runs identically offline (deterministic mock) and on real NIM.

02

The four harnesses

Each harness is a standalone script under src/eval/, run with pnpm eval:<name>. It scores the live AI plane against planted ground truth, prints the numbers, and exits non-zero if any gate is missed — so the same script that reports the score can block the release.

What each one actually checks

1

Extraction — barrier-type F1

For every labelled note it calls /extract, compares the extracted barrier types against the planted set, and computes precision / recall / F1 plus MFFD accuracy. F1 balances the two failure modes — missing a real barrier versus inventing one.

Why this metric Extraction can fail in two opposite directions: it can miss a real barrier (low recall) or invent one that isn’t in the note (low precision). A single accuracy percentage averages those together and hides whichever is worse — you could ship a model that quietly drops a third of the barriers and still read a healthy-looking score. F1 is the harmonic mean of precision and recall, so it only stays high when both failure modes are low; it cannot be gamed by trading one off against the other.

2

Copilot — hit-rate, groundedness, query-intent

The policy path embeds each question, runs the pgvector cosine top-K (K = 8), reranks to top-N (N = 4), and checks the expected policy document was retrieved (hit-rate) and the answer came back grounded. The ward path sends each question to /copilot/query-intent and checks the produced structured filter matches the expected keys. Retrieval is only useful if the right passage returns, and an answer is only safe if it is grounded in what was retrieved — both are scored.

Why this metric This is the RAGAS split — retrieval quality and answer quality are two different failures and must be measured apart. Hit-rate asks “did the right passage come back at all?” — if retrieval whiffs, no amount of eloquence can save the answer. Groundedness asks “is every claim in the answer traceable to a retrieved passage?” — a model can retrieve the correct document and still hallucinate around it. A single “did it answer well?” score would let a fluent, confident, wrong answer pass; splitting them tells you which half broke, which is what you need to fix it.

3

Actions — appropriateness & grounding

For each labelled barrier it retrieves policy and calls /agent/recommend, then checks the recommended action_type matches the expected mapping and the rationale is grounded in a cited passage.

Why this metric An action recommendation has two independently-failing parts: what it recommends and why. Appropriateness scores the “what” against the expected barrier → action mapping; rationale-grounding scores the “why” against an actual cited policy passage. Scoring only appropriateness would let a right answer through with an invented justification — dangerous in a clinical setting, where an ungrounded rationale is a fabricated reason to act.

4

Forecast & narration — Spearman ρ + numeric-consistency

The deterministic discharge model is scored on getting the order right (Spearman ρ against a truth score), not on hitting an exact probability, because the forecast is used to rank patients. Then the narrator is fed a fixed set of numbers and the briefing is checked so that every integer it states came from the input — proving the LLM narrates and never invents figures.

Why this metric The forecast’s job is to order patients by how ready they are for discharge — a coordinator reads the list top-down. So what matters is rank, not the absolute probability. Spearman ρ measures exactly that: it scores whether the model puts patients in the same order as the truth, and is indifferent to whether it said 0.7 or 0.9 for the top patient. Grading on an exact-probability error (like RMSE) would punish a model that ranks perfectly but is systematically cautious, and reward a model that hits the numbers yet scrambles the order — the opposite of what the feature needs.

Why this metric A narrator has essentially one way to be dangerous: state a wrong number — “4 beds free” when there are 2. Fluency and tone don’t matter clinically; a misquoted figure does. Numeric-consistency targets that single failure directly by asserting every integer in the briefing was present in the input, proving the LLM is narrating supplied facts, not computing or inventing them.

03

Running the evals

The harnesses hit the running AI plane and read planted labels from Postgres, so bring both up and seed first. Each eval then runs as its own command and prints its numbers before it exits.

docker compose up -d db ai      # Postgres + the FastAPI AI plane
pnpm db:migrate
pnpm db:seed:ward               # labelled synthetic ward → extraction + forecast labels
pnpm db:seed:policy             # discharge-policy KB (pgvector) → copilot + action evals

pnpm eval:extraction            # F1 gate 0.85
pnpm eval:copilot               # hit-rate / grounded / query-intent, gates 0.90
pnpm eval:actions               # appropriateness / grounding, gates 0.90
pnpm eval:forecast              # Spearman ρ 0.70 / numeric-consistency 0.90

Any gate miss exits non-zero (and prints the shortfall), so these can be wired into CI unchanged when CI is re-introduced.

What a gate is (and why it exits non-zero)

A gate is a threshold the measured number must clear — F1 ≥ 0.85, groundedness ≥ 0.90, Spearman ρ ≥ 0.70. If the number falls short, the harness prints the shortfall and exits with a non-zero status code. That exit code is the whole point: it is the language every shell, Makefile, and CI runner already understands as “this step failed.” A green run is a machine-checkable promise that the AI still meets the bar; a red run stops the pipeline before a worse model reaches production. Because the exact same script both reports the score and returns the exit code, there is nothing extra to wire up — the report is the gate.

Why this matters A gate is only worth having if it can actually fail. Set the threshold where the model comfortably always passes and you have a green light that means nothing — it will stay green straight through a regression. The thresholds here sit just below current live performance: high enough that a real drop trips them, low enough that healthy natural variance doesn’t. A gate you never fail is not a gate; it’s decoration.

Mock vs live. By default the AI plane runs the deterministic offline mock (NIM_MOCK=true, or no NVIDIA_API_KEY) — the evals still run and exercise the full pipeline. To evaluate the real models, set NIM_MOCK=false and a NVIDIA_API_KEY, recreate the ai container, and re-run. The figures on this page are the live NIM numbers.

Why both The mock is deterministic, free, and offline, so the harness always has something to run — it proves the whole pipeline (dataset → AI plane → metric → gate) is wired correctly even with no API key, and keeps the scoring/parsing/gate logic honest without spending a token. But a mock returns canned outputs, so a green mock says nothing about whether the real model is good enough. That is why the headline figures on this page are the live-NIM numbers: the mock proves the harness works; live NIM proves the AI works.

The eval loop

Every harness is the same shape: a labelled dataset feeds the live AI plane, the output is scored into a metric, and the metric is compared to its gate — pass continues, fail exits non-zero.

04

Measured, not guessed

The point of a number is that it moves. When it moves the wrong way, a hard gate makes the regression impossible to ship past — and impossible to miss.

Measured, not guessed. The extraction harness earned its keep early: it caught the first model choice underperforming and let the prompt be tuned from a measured 69% to 88% F1. Without the number, that regression would have been invisible — the model would have felt fine and quietly missed a fifth of the barriers.

Walk through what happened. The first model choice extracted barriers that read correctly — plausible types, sensible language — and on a spot-check it looked done. But scored against the planted labels it landed at 69% F1, meaning it was quietly missing or inventing close to a third of the barriers. That number is the only reason anyone knew. With the gap made visible, the fix was mechanical rather than a guess: swap the model and tune the prompt, re-run the harness, and watch the number climb to 88%, clearing the 0.85 gate. The lesson is not “our first model was bad” — it is that the failure was measurable, and therefore fixable. A team relying on the demo feeling would have shipped 69% and never known; the harness turned an invisible regression into a two-line diff and a number that moved.

The lesson You cannot improve what you don’t measure, and you cannot catch a regression you can’t see. The 69% was not a disaster — it was the harness doing its job, on day one, on exactly the kind of silent quality loss that a spot-check will always wave through.

Why these metrics (and not others)

Each metric is chosen to match how its output is actually used — a single accuracy number would hide the failure that matters.

F1 for extraction

Extraction can fail two ways — missing a real barrier or inventing one. F1 balances recall against precision, so neither is hidden. A single accuracy number would mask one of them.

Hit-rate & groundedness for RAG

The RAGAS-style split separates “did retrieval work” from “is the answer safe.” Retrieval is only useful if the right passage comes back, and an answer is only safe if grounded in it — so both are scored.

Rank correlation for the forecast

The forecast is used to order patients by dischargeability, so it is scored on getting the order right (Spearman ρ), not on a false-precision point estimate.

Numeric-consistency for narration

The one failure that matters for a narrator is stating a wrong number. Checking that every figure came from the input targets exactly that.

Adding a new eval

Every harness follows the same five-step pattern, so a new one is a copy-and-adapt rather than a design exercise. To evaluate a new AI capability:

1

Plant ground truth

Add a labelled dataset — inputs paired with the known-correct answer — usually as synthetic rows in a seed (notes.eval_labels) or a fixture the harness reads. This is the “truth” the score is measured against, so label it carefully; the eval is only as honest as its labels.

2

Pick a metric that fits the use

Ask how the output is actually consumed, then choose the metric that exposes the failure that matters — F1 for “must not miss or invent,” a rank correlation for “must order correctly,” a grounding check for “must not fabricate.” Resist a bare accuracy number; it averages away the failure you care about.

3

Write the harness

Copy an existing script under src/eval/: load the labels, call the live AI-plane endpoint for each case, score the output into your metric, and print the numbers. Keep it a plain standalone script — no test framework needed.

4

Set a gate and exit non-zero

Choose a threshold just below current live performance and process.exit(1) when the metric falls short. This is what turns a report into a release gate — and makes it CI-ready with no extra wiring.

5

Wire the command

Add a pnpm eval:<name> script so it runs alongside the others, then record the live figure. That number is now part of the definition of “working.”

05

Next steps

The harness is deliberately small and honest — enough to gate the current capabilities against the live models. The natural next moves make it stricter, more automatic, and more representative over time.

Evals in CI

Run every eval:* on each pull request, so a model or prompt change that drops a metric fails the build before it can merge — the gate stops being a manual step and becomes automatic.

RAGAS faithfulness

Move the copilot grounding check from an exact-passage test to a proper faithfulness score, measuring how well every claim in an answer is entailed by the retrieved context rather than merely present.

LLM-as-judge

For open-ended outputs where there is no single right string — rationales, narration tone — add a rubric-scored model judge, cross-checked against human labels so the judge itself is validated, not trusted blindly.

Regression tracking over time

Persist each run’s figures so metrics can be trended, not just gated — a slow month-over-month slide that never quite trips a threshold is exactly the drift a single pass/fail line can miss.

Bigger, real-derived sets

Grow the labelled datasets and derive them from de-identified real notes rather than purely synthetic ones, so the score reflects the messiness the model meets in production, not a clean best case.
