How it is built

WardBeat is built spec-first on a trunk-based git workflow, with a hard local quality gate — lint, types, tests, build, and the AI evals — standing between every change and a release tag.

01

Spec-driven development

Non-trivial work on WardBeat starts with a short written spec that captures the what and why before anyone writes the how. The rule is simple: a new capability, a security-posture change, an infrastructure move, or a notable trade-off gets a spec; a trivial fix, a dependency bump, or a copy edit does not — a good commit message is enough there. The point is to make intent reviewable, keep scope honest, and leave the codebase a durable record of the decision behind each release.

Writing the contract before the code is the whole discipline. It reduces rework, because disagreements about scope surface on a page you can edit in minutes rather than in code you have to unpick over a day. It forces the why to be stated out loud, so a reviewer can push back on the goal, not just the diff. And it turns review into a conversation about intent — is this the right thing to build? — instead of a line-by-line hunt through an implementation that may already be pointed at the wrong target.

Two files for a release, one for a one-off

A WardBeat release is planned as a folder under specs/releases/vX.Y.Z-slug/ holding two files that do deliberately different jobs. Splitting them keeps the frozen agreement apart from the plan that keeps moving.

spec.md — the contract

The what & why: summary, problem, goals, non-goals, scope, requirements, acceptance criteria, security. Frozen once it reaches Accepted — the agreed target the work is measured against.

spec-imp.md — the plan

The how: approach, architecture deltas, milestones, data model, interfaces, the test & eval plan, and a Definition of Done. A living document, updated as the work proceeds.

Why the split A contract you keep editing is not a contract. Freezing spec.md at Accepted means the acceptance criteria cannot quietly drift to match whatever got built — the finished work is held to what was actually agreed. Meanwhile spec-imp.md is expected to change as reality intrudes: it is where a discovered constraint or a better approach gets recorded without touching the agreement.

One-off changes and the numbered history

A one-off change that still deserves a written intent — but is not a whole release — uses the flat specs/TEMPLATE.md, copied to NNNN-slug.md and opened as Proposed. The numbered specs 0001–0025 are history: 0001–0024 document the platform foundation WardBeat inherited, and 0025 is WardBeat’s own foundation spec. From v0.2.0 onward, every WardBeat release lives in its own specs/releases/vX.Y.Z-slug/ folder as the two-file pair.

Spec is intent-before; changelog is record-after. The spec says why and what, written before the work. The CHANGELOG.md entry says what shipped, written for users after. They complement each other — neither is a substitute for the other, and a release fills in both.
02

Trunk-based git

WardBeat is deliberately trunk-based, not GitFlow. main is the only long-lived branch — there is no develop, release, or hotfix. Feature work branches off main as feature/<slug>, and opens a pull request straight back into main. A release is nothing more than a vX.Y.Z tag on a main commit; the tag is what defines the release. There is no required Release vX.Y.Z merge commit — a plain commit on main can be tagged directly.

The reason to work this way is that integration stays cheap and main stays releasable. Long-lived branches drift apart and turn merges into archaeology; a single trunk that everyone rejoins quickly keeps that drift small and the history honest. Because a release is just a tag on a good commit, cutting one is a labelling act, not a branch-management ceremony.

Commits, hooks, and the changelog

Conventional Commits

Every commit follows feat:, fix:, docs:, chore:… enforced by a commitlint commit-msg hook. Body lines stay ≤ 100 characters, so the history reads cleanly and can be parsed by tooling.

pre-commit runs lint-staged

A Husky pre-commit hook runs ESLint + Prettier on staged files before the commit lands, so formatting and lint drift never enters the trunk in the first place.

Keep a Changelog

CHANGELOG.md follows the Keep a Changelog format and is updated for every user-facing change — the after-the-fact record that pairs with the before-the-fact spec.

No AI credit in git

No Co-Authored-By: Claude, no “Generated with…”, no assistant trailer of any kind on commits or PR descriptions. The history reads as human-authored work.

Cutting a release

Bump the version, set the spec to Shipped, update CHANGELOG.md, then tag a main commit vX.Y.Z and push it. Pushing a v* tag is what triggers deploy when CI is wired; the pre-1.0 stream today is a series of such tags on main.

git checkout main && git pull
git checkout -b feature/<slug>
# ...write the spec, implement, run the gate...
git commit -m “feat: add flow copilot”      # Conventional Commits, body lines ≤ 100
# open a PR into main, merge once the gate is green
# then, on main, cut the release:
git tag -a vX.Y.Z -m “short title”
git push origin main --tags                 # the v* tag defines the release

Why trunk-based A trunk that is always releasable means there is never a “stabilise the release branch” phase — the last green commit is shippable by definition. That is only safe because the quality gate below is hard, which is what section 03 is about.

03

The quality gate

Before pushing, one command has to pass end to end. It is the contract that keeps main releasable, and — because CI is deferred at this stage — it is the gate that actually matters today. It runs locally, on the developer’s machine, and nothing goes onto the trunk that has not cleared it.

pnpm lint && pnpm typecheck && pnpm test && pnpm build

Each stage catches a different class of mistake, and chaining them with && means the first failure stops the line — you never ship having only run half the checks.

lint

eslint . — catches the class of bug a linter sees and enforces the house style, so review is about behaviour, not formatting.

typecheck

tsc --noEmit in strict mode — the type system rejects whole categories of runtime error before the code ever runs.

test

vitest run over tests/unit — the behavioural safety net; pnpm test:e2e (Playwright) adds the full-stack pass.

build

next build — proves the production build actually compiles, catching failures that only surface outside next dev.

The AI-specific gates

WardBeat has AI capabilities, and a passing type-check says nothing about whether a model still reads a note correctly. So two more gates sit alongside the standard four: the four eval harnesses and the FastAPI service’s own test suite. Because AI quality is measured, not assumed, these are gates, not dashboards — each harness exits non-zero when its gate is missed.

Four eval:* harnesses

eval:extraction, eval:copilot, eval:actions, and eval:forecast each run a labelled synthetic dataset through the live NVIDIA NIM models, score a metric that fits the task, and fail if the gate is missed — F1 ≥ 0.85 for extraction, ≥ 0.90 for RAG and actions, Spearman ρ ≥ 0.70 for the forecast.

The ai/ pytest suite

The FastAPI AI service has its own Python tests — ai/tests/test_extract.py, test_forecast.py, test_config.py — covering the service boundary and the deterministic forecast maths that must never be left to the model.

A hard gate is what makes trunk-based safe. With CI deferred, there is no server-side net to catch a bad push — so the local gate has to be non-negotiable. Because every commit on main has cleared lint, types, tests, build, and the evals, the last green commit is always a candidate release. That is the whole bargain: a hard gate buys an always-releasable trunk.
04

The loop, end to end

Put together, the practices form one repeatable loop from a written intent to a live release. The diagram traces a single change through it; each stage exists to make the next one safe.

1

Spec — the what & why

A non-trivial change opens with spec.md, agreed and frozen at Accepted. It exists so the target is settled before effort is spent — review argues about the goal while it is still cheap to change.

2

Branch off main

Work happens on feature/<slug>, cut from main. There is no long-lived branch to integrate against, so the branch stays short and rejoins the trunk quickly.

3

Implement against spec-imp

The code is written to the plan in spec-imp.md, which is updated as reality intrudes. The frozen contract stays the yardstick; the plan is free to move.

4

Run the local gate

lint · typecheck · test · build, plus the four evals and the ai/ pytest suite. This is the hard stop — nothing pushes that has not cleared it, which is what keeps the trunk releasable.

5

Update the CHANGELOG

Every user-facing change gets a Keep a Changelog entry — the after-the-fact record that pairs with the before-the-fact spec, so users can see what shipped.

6

PR into main, then merge

A pull request goes straight into main — no develop to target. Because the spec captured the intent, review is about whether this is the right thing, merged once green.

7

Tag vX.Y.Z, deploy

On main, a vX.Y.Z tag is the release — bump the version, mark the spec Shipped, and push the tag. Pushing the v* tag is what triggers deploy when CI is wired.

05

Other ways to build it — with AI agents

The spec → branch → gate loop above is the backbone, but it is not the only shape the work can take. Increasingly the fastest way to build is to fan the work out across AI coding agents and orchestrate them — and this guide itself was built that way, one agent per tab, in parallel. The patterns below change who holds the keyboard; the discipline around the code stays exactly the same.

The patterns

Git worktrees

Isolation

git worktree add ../wt-feature feature/x checks a second branch out into its own directory, sharing one repository. You get several branches live at once — no stashing, no switching the working tree out from under in-progress work.

  • Why it matters. It lets multiple tasks — or multiple agents — edit files at the same time without stepping on each other; each works in a clean, isolated copy and merges back once green. Agent tooling can hand each agent its own worktree automatically and discard it if nothing changed.

Instead of stashing and branch-switching a single working tree, which serialises everything and risks losing in-progress state.

Parallel agents (fan-out)

Breadth & speed

Scope a set of independent tasks and run an agent on each at once; an orchestrator collects and composes the results. WardBeat’s guide tabs were authored this way — one agent per page — as were the documentation audit and the diagram-overlap fixes.

  • Why it matters. Wall-clock collapses to the slowest single task instead of the sum, and each agent keeps a small, focused context rather than one thread holding everything at once.
  • Adversarial verification. Spin up independent agents to try to refute a finding, and keep only what survives — diversity of perspective catches what a single pass misses.

Instead of one agent doing everything sequentially — slower, and its context fills with unrelated detail until quality drops.

Orchestrated workflows

Reproducible

For bigger jobs, a deterministic script drives the agents: fan out, pipeline stages (understand → design → implement → verify), loop until a target is met. The control flow is code; the agents are the workers.

  • Why it matters. It makes a multi-agent run repeatable and reviewable, and scales to work a single context could never hold — a broad migration, an exhaustive review, an audit across the whole tree.

Spec-driven, with agents

On target

The spec from section 01 is the contract an agent implements. Point an agent at a spec.md and it builds to the what and why; review stays about intent, not archaeology.

  • Why it matters. The discipline that keeps a human on target keeps an agent on target too — the spec is the shared source of truth, whoever holds the keyboard.
However it is produced, it goes through the same gate. Fan-out and agents change who writes the code, not the bar it has to clear. Every change still runs lint · typecheck · test · build plus the eval gates, and is still reviewed and committed the same way. The guard rails in sections 01 and 03 are exactly what make it safe to let more hands — human or AI — touch the code.
06

Why this way

Each practice earns its place by preventing a specific failure. Together they are what lets a small team ship a clinical-facing AI product with a straight face — intent is written down, the trunk is always releasable, and quality is a number the release is measured against.

Spec-first

Intent before code

A written spec.md contract (what & why) and a living spec-imp.md plan (how) for every non-trivial change.

  • Less rework. Scope disagreements surface on an editable page, not in code you unpick later.
  • The why is explicit. Reviewers can push back on the goal, not just the diff.
  • Frozen contract. Acceptance criteria cannot drift to match whatever got built.

Trunk-based git

One long-lived branch

Feature branches off main, PRs straight back, and a release is a vX.Y.Z tag on a main commit.

  • Cheap integration. Short branches rejoin quickly, so merges stay small.
  • Always-releasable main. No stabilise-the-release-branch phase — the last green commit ships.
  • Releasing is labelling. A tag defines the release; no branch ceremony.

Hard local gate

lint · type · test · build

One chained command that must pass before any push, standing in for CI while it is deferred.

  • Nothing bad on the trunk. A failing stage stops the line before code lands.
  • Production build proven. next build catches what next dev hides.
  • Trunk stays shippable. The gate is what makes trunk-based safe.

Evals as gates

Four harnesses + pytest

Each AI capability is pinned to a metric and a threshold; the harness exits non-zero when the gate is missed.

  • Quality is a number. An unmeasurable AI feature is one you cannot defend.
  • Regressions caught. A tuned prompt took extraction from 69% to 88% F1 — visible only because it was measured.
  • No silent drift. A model change that lowers a score fails the gate.

Conventional Commits + changelog

Readable history

Commitlint-enforced feat:/fix: messages (≤ 100-char bodies) and a Keep a Changelog record for every user-facing change.

  • Parseable history. Consistent prefixes let tooling read the log.
  • Record after intent. The changelog pairs with the spec — why before, what shipped after.
  • Human-authored. No AI credit trailers; the history reads as real work.

The payoff

Defensible delivery

The combined effect: a clinical-facing AI product that can be shipped with confidence and explained after the fact.

  • Every release is traceable. Spec, gate, changelog, and tag form one chain.
  • Nothing ships unmeasured. Both code and AI quality are gated.
  • Fast without being reckless. A short loop that never skips the checks.
